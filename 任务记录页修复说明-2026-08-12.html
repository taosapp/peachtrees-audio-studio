🍑 PeachTrees 任务记录页修复说明

2026-08-12 · 修复合成期间任务列表卡 loading + 新增时长列

问题 1：合成期间任务记录页整页 loading 的根因

提交合成任务后，后台任务 _process_tts_sync 由 FastAPI BackgroundTasks 以协程形式运行在事件循环中，但它直接同步调用了 tts_service.generate_speech()——该函数内部会阻塞轮询等待 worker 子进程返回结果（最长 300 秒）。

结果：合成期间整个事件循环被占死，所有 API 都无法响应（任务列表、状态查询、下载全部挂起）。前端请求一直 pending，v-loading 遮罩就转个不停，看起来"整个列表在 loading"。

✗ 修复前
事件循环被同步合成调用阻塞 → 列表接口 300s 内不返回 → 整页 spinner，历史任务也看不到。
✓ 修复后
generate_speech 放入线程池（asyncio.to_thread）→ 事件循环保持响应 → 列表秒回，历史任务立即可见。

修复方案

asyncio.to_thread
同步合成调用移入线程池执行
单项 spinner
仅进行中任务显示加载图标
5s 轮询
有进行中任务时列表自动静默刷新
2 个时长字段
音频时长 + 合成耗时

问题 2：任务列表新增时长列

任务记录列表新增两列：

列名数据来源说明
音频时长tts_duration_sec（已有字段）合成出的音频长度，历史任务已有数据，格式如 34.0 秒 / 1:23
合成耗时elapsed_sec（新增字段）提交 → 完成的过程耗时，秒级精度；旧任务无数据显示 —

改动文件清单

文件改动
backend/api/v1/tasks.py① generate_speech 改用 await asyncio.to_thread(...)；② 合成开始/结束记录耗时写入 elapsed_sec（成功与失败都记录）；③ 列表接口新增 status 过滤参数；④ 列表/详情接口返回 tts_duration_sec、elapsed_sec
backend/models/task.py新增 elapsed_sec 字段（合成过程耗时，秒）
backend/core/database.py新增 ensure_schema()：老库自动 ALTER TABLE 补列（幂等）
backend/main.py启动 lifespan 调用 ensure_schema()
frontend/src/views/Tasks.vue① 状态列：排队中/处理中显示单项 spinner + 文字；② 新增"音频时长""合成耗时"两列；③ 存在进行中任务时每 5s 静默刷新，全部结束自动停止；④ 状态筛选下拉真正生效（此前参数被前端丢弃）；⑤ 轮询失败静默不弹错

验证结果

  • ✓ 数据库迁移：真实库执行 ensure_schema() 两次均幂等通过，elapsed_sec 列存在且可读写（历史任务该列为 NULL，属预期）
  • ✓ 后端 API 冒烟：GET /api/v1/tasks 返回 200，携带 tts_duration_sec / elapsed_sec 字段；status=done 过滤生效（返回全部为 done）
  • ✓ 前端 vite build 构建通过（Tasks 组件编译无错误）
  • ✓ 全部 Python 文件 py_compile 语法检查通过

⚠ 合成期间事件循环不再阻塞这一行为，需重启后端后在真实合成场景下确认（见下方重启步骤）。

重启步骤

  • 后端：运行 manage.bat → 选 3（重启前后端服务），或手动重启 FastAPI（python backend/main.py）
  • 前端：若用 Vite dev server（5173 端口），无需重启，热更新自动生效；若用构建产物，重新 npm run build 即可
  • 数据库无需手动操作：首次启动会自动补列
